## 1. 애초에 뭘 하려는 프로젝트인가

회사가 "직원들이 사내 PC에서 Claude/ChatGPT/Gemini 같은 AI 서비스에 어떤 파일을 업로드하는지"
감시하고 싶다고 가정합니다. 그러려면 직원 PC와 AI 서비스 사이를 오가는 네트워크 트래픽을
들여다봐야 합니다.

문제는 요즘 웹/앱 통신은 전부 **HTTPS(암호화)**라서, 중간에서 가로채도 암호문만 보입니다.
그래서 쓰는 기법이 **로컬 프록시를 이용한 MITM(중간자)**입니다.

## 2. MITM 프록시가 뭔가

```
[내 PC의 브라우저/앱]  ──▶  [내 PC에서 돌아가는 프록시 프로그램]  ──▶  [진짜 Claude 서버]
       (A)                        (127.0.0.1:18080)                    (B)
```

- 브라우저/앱은 프록시를 "진짜 서버"라고 믿고 통신합니다 (A 구간)
- 프록시는 그 내용을 평문으로 까본 다음, 다시 암호화해서 진짜 서버로 전달합니다 (B 구간)
- 이게 가능하려면 브라우저/앱이 "이 프록시의 인증서를 신뢰"하게 만들어야 하는데, 회사
  PC에 미리 심어둔 사내 rootCA로 그걸 해결합니다

여기서 **127.0.0.1**은 "내 컴퓨터 자기 자신"을 가리키는 특수 주소입니다 (루프백 주소).
프록시가 내 PC 안에서 돌고 있으니, 앱은 `127.0.0.1:18080`으로 연결하게 되는 겁니다.

## 3. 그런데 왜 하필 "MSIX 앱"이 문제였나

Claude Desktop 같은 앱은 두 가지 설치 방식이 있을 수 있습니다:
- 그냥 exe 설치 (제약 없음)
- **MSIX**(Microsoft Store 패키지 형식)로 설치 — 이건 Windows가 자동으로
  **AppContainer**라는 샌드박스 안에 앱을 가둡니다

샌드박스는 "이 앱이 나쁜 짓을 해도 시스템 전체에 피해가 안 가게 격리한다"는 보안
장치입니다. 그리고 Windows는 이 샌드박스 안 앱들에 대해 아주 오래된 보안 정책 하나를
갖고 있습니다:

> **"같은 컴퓨터 안의 다른 프로세스(127.0.0.1)에 함부로 말 걸지 마라"**

이게 바로 루프백 차단입니다. 일반 인터넷(원격 서버)에 나가는 건 허용하면서, 유독
**자기 자신(127.0.0.1)에 말 거는 것**만 막습니다.

## 4. 그래서 처음에 무슨 일이 벌어졌나

```
Claude Desktop(MSIX) ──(127.0.0.1:18080 프록시로 연결 시도)──▶  ✕ 여기서 Windows가 차단
```

프록시 설정 자체는 정상이었는데, OS가 애초에 "너는 루프백에 말 걸 수 없어"라며 연결
자체를 끊어버린 겁니다. 그래서 캡처가 0건이었습니다. (브라우저는 MSIX 샌드박스에 안
갇혀 있으니 이 문제가 없었고, 그래서 웹은 처음부터 잘 잡혔던 것)

## 5. 그럼 어떻게 뚫었나

Windows에는 이 차단에 대한 **공식 예외 등록 명령**이 원래 있었습니다 (개발자들이 로컬
테스트할 때 쓰라고 마이크로소프트가 만들어 둔 것):

```
CheckNetIsolation LoopbackExempt -a -n=Claude_pzs8sxrjxfjjc
```

이건 "Claude 패키지는 루프백 통신을 허용 목록에 넣어줘"라고 Windows에게 등록하는
명령입니다. 이걸 실행하니:

```
Claude Desktop(MSIX) ──(127.0.0.1:18080)──▶ ✅ 통과 ──▶ 우리 프록시가 정상 캡처
```

캡처해보니 Claude Desktop이 내부적으로 Electron(=크롬 엔진)을 쓰기 때문에,
웹브라우저로 업로드할 때와 **완전히 동일한 데이터**를 보낸다는 것까지 확인됐습니다.

## 6. 이게 왜 중요한가 (핵심 주장)

여기서 짚어야 할 미묘한 포인트가 있습니다: **이 차단은 "뚫을 수 없는 벽"이 아니라
"이번 PoC의 배치 방식(로컬 127.0.0.1 프록시) 때문에 생긴 우연한 제약"**이라는 겁니다.

- 만약 프록시를 127.0.0.1이 아니라 **다른 호스트(예: 사내 서버)**에 뒀다면 → 이건
  "루프백"이 아니라 "일반 인터넷 연결"로 취급되니 → 애초에 이 차단 규칙이 적용 안 됩니다
- 나중에 계획 중인 **WFP(커널 레벨 리다이렉트)** 방식을 쓰면 → 앱은 "나는 그냥
  인터넷에 연결하는 중"이라고만 알고, 프록시라는 개념 자체를 인지하지 못하니 → 역시
  이 차단과 무관합니다

즉 이번 발견의 의미는 "MSIX 앱도 결국 다 뚫린다"가 아니라, **"우리가 지금 쓰는
방식(로컬 프록시)의 특정 제약 하나를 확인했고, 그 제약이 실제 서비스 배포 방식에서는
애초에 문제가 안 된다는 걸 증명했다"**는 겁니다.

반면 진짜 못 넘는 벽은 따로 있습니다:
- **인증서 고정(pinning)**: 어떤 앱은 "나는 이 특정 인증서만 믿어"라고 하드코딩돼
  있어서, 사내 rootCA를 아무리 심어도 안 통합니다
- **QUIC 강제**: 프록시가 가로챌 수 있는 건 TCP 트래픽인데, 일부 서비스는 QUIC(UDP
  기반)을 강제해서 애초에 프록시 경로를 안 탑니다

이 둘은 배포 방식(로컬 프록시든, 다른 호스트든, WFP든)과 무관하게 **원천적으로 안 되는
것**이라, MSIX 샌드박스 문제와는 성격이 다릅니다.

## 7. 마지막 "감청" 논의

기술적으로 "회사가 직원 AI 앱 사용을 들여다볼 수 있는가"는 이미 실증(YES)됐지만,
이걸 실제로 회사가 상품화해서 쓰려면:
- **회사 소유 기기 + 사전 고지/동의**가 있으면 → 이건 Zscaler 같은 회사들이 이미
  파는 정상적인 "기업 보안 모니터링" 제품
- **고지 없이** 하면 → 법적으로 "감청" 리스크

즉 기술 자체는 검증 끝났고, 남은 건 **엔지니어링 문제가 아니라 회사가 이걸 어떤
정책(고지·동의)으로 감싸서 배포하느냐는 법무/인사 문제**라는 게 결론입니다.
