# MSIX 앱 가시성 — 무슨 일이 있었고, 제품화 관점에서 무엇을 의미하는가

> **작성일:** 2026-07-28
> **계기:** claude-app(MSIX/Electron) 캡처 성공 사례를 다시 짚으며, "그럼 회사가 이걸 제품화하면
> AI 앱 감청이 가능하다는 뜻이냐"는 질문에 답하는 과정에서 정리됨
> **성격:** 기술 설명 + 제품화 판단 기록

---

## 1. 실제로 무슨 일이 있었나

MSIX(Store) 앱은 **AppContainer 샌드박스**에서 돕니다. Windows는 이 샌드박스에서 나가는
`127.0.0.1`(루프백) 연결을 **기본 차단**합니다.

이건 앱이 프록시 설정을 무시하는 것(유형 A)도, 인증서를 거부하는 것(유형 B)도 아닙니다.
**OS가 애초에 경로 자체를 끊어버리는 것**이라 별도 유형 **(D) OS 샌드박스 격리**로 분류했습니다.

그런데 (D)는 Windows에 알려진 우회법이 있었습니다.

```
CheckNetIsolation LoopbackExempt -a -n=Claude_pzs8sxrjxfjjc
```

이 명령으로 Claude 데스크톱 앱 패키지에 "루프백 예외"를 등록하면, 샌드박스가
`127.0.0.1:18080`(우리 프록시) 접근을 허용합니다. 이거 하나로 결과가 완전히 갈렸습니다.

| | 예외 등록 전 | 예외 등록 후 |
|---|---|---|
| 캡처 | 0건 (프록시 도달조차 못함) | **웹과 100% 동일하게 완전 포착** |

등록 후 캡처해보니 앱이 웹 버전과 **바이트 단위로 똑같은** multipart 업로드를 보냈습니다
(오버헤드 204B 동일, 해시 동일). Claude Desktop이 Electron이라 내부적으로 Chromium을
쓰기 때문입니다.

### (D)의 정확한 의미

"탐지 불가능"이 아니라 **"로컬 127.0.0.1 프록시라는 PoC 배치 방식 자체의 제약"**입니다.
실제 사내 배포에서는 프록시가 별도 호스트에 있거나 WFP로 커널 레벨에서 리다이렉트하니
애초에 이 루프백 제한에 걸리지 않습니다. 오히려 이 발견이 "왜 다음 단계로 WFP가 필요한가"를
실측으로 정당화하는 근거가 됐습니다.

**정정해 둘 점:** 유형 A(QUIC 우회)·B(인증서 고정)는 로컬 프록시로 정말 못 넘는 벽이고,
유형 D(MSIX 샌드박스)는 이번처럼 **경로 하나 열어주면 완전히 해소되는 벽**입니다 —
성격이 다르므로 뭉뚱그려 "똑같이 무의미하다"고 말하면 안 됩니다.

---

## 2. 정확한 그림 — 무엇이 막혔고, 무엇을 열었나

우리 프록시는 애초에 루프백 주소(`127.0.0.1:18080`)에서 돌고 있습니다. MSIX 앱이 이
주소로 연결하려는 게 시스템 프록시 설정으로 잡히는데, Windows AppContainer 샌드박스는
**바로 이 루프백 목적지 연결을 기본 차단**합니다.

```
MSIX 앱 ──(연결 시도)──▶ 127.0.0.1:18080 (우리 프록시)
              ↑
          AppContainer가 여기서 차단
          ("같은 머신 위 서비스에 말 걸지 마라" — 옛날부터 있던 UWP 보안 정책)
```

`CheckNetIsolation LoopbackExempt` 명령이 하는 일은 **"이 앱은 루프백 예외로 봐줘"**라고
등록하는 것입니다. 그래서 등록 후엔 같은 루프백 프록시(127.0.0.1)에 정상 연결됐습니다.

### 왜 실제 배포에선 이 문제가 안 생기나

MSIX 샌드박스는 **루프백만** 특별 취급해서 막습니다. 일반 인터넷 연결(원격 호스트, 즉
루프백이 아닌 주소)은 대부분의 앱이 갖고 있는 `internetClient` 권한으로 **처음부터
허용**돼 있습니다.

그래서:

- **프록시가 루프백(127.0.0.1)에 있으면** → 차단됨 → 예외 등록 필요 (지금 우리 PoC 상황)
- **프록시가 다른 호스트(루프백 아닌 주소)에 있으면** → 애초에 이 제약에 안 걸림 →
  예외 등록 자체가 불필요
- **WFP로 커널에서 가로채면** → 앱이 "프록시에 연결"한다는 개념 자체가 없어짐(앱은 그냥
  인터넷에 연결한 줄 알고, 커널이 몰래 가로챔) → 역시 이 제약과 무관

**한 줄 정정:** "프록시는 못 쓰고 루프백은 쓸 수 있다"가 아니라, **"루프백에 있는 프록시는
예외 등록 없인 막히고, 루프백이 아닌 곳에 있는 프록시(또는 프록시 개념 자체가 없는 WFP
방식)는 처음부터 안 막힌다"**가 정확합니다.

## 3. WFP만이 유일한 방법인가 — 아니다

정리하면 앱 통신을 볼 수 있는 경로가 최소 3가지다.

| 방법 | 원리 | 상태 |
|---|---|---|
| **① 루프백 프록시 + 예외 등록** | `CheckNetIsolation LoopbackExempt`로 그 앱만 봐달라고 등록 | **이미 실증함** — claude-app 캡처가 이 방식으로 100% 성공 |
| **② 루프백 아닌 주소의 프록시** | 프록시를 다른 호스트나 127.0.0.1이 아닌 IP에 놓음 → AppContainer의 루프백 차단 자체가 애초에 적용 안 됨 | 이론상 성립, 아직 직접 검증은 안 함 |
| **③ WFP 커널 리다이렉트** | 앱은 "인터넷에 연결한다"고만 알고, 커널이 몰래 프록시로 우회시킴 — 프록시라는 개념 자체가 앱 입장에서 안 보임 | 아직 미구현(계획 단계) |

**①로 이미 앱 통신을 완전히 봤다** — WFP가 없어도 됐다. 다만 ①의 실전 단점은:

- MSIX 앱마다 **패키지 이름을 알아내서 하나하나 예외를 등록**해야 함 (관리자 권한 필요)
- 새 앱이 설치될 때마다 수동으로 추가해야 함 → 사내 수백 대에 배포하기엔 안 맞음

그래서 WFP가 필요한 이유는 **"안 보여서"가 아니라 "①은 앱별 수동 등록이라 규모가 안
나와서"**다. WFP(또는 ②처럼 프록시를 별도 호스트로 옮기는 것)는 **한 번 설정하면 앱이
늘어나도 자동으로 잡힌다**는 운영 편의성 문제를 푸는 것이지, 기술적으로 유일한 가시성
확보 수단은 아니다.

## 4. 제품화하면 "앱 감청"이 가능하다는 뜻인가

기술적으로는 "예"에 가깝지만, **기술적 한계**와 **법적 프레이밍**은 서로 다른 문제라
나눠서 답해야 한다.

### 4.1 기술적으로 — 어디까지 실증됐나

| 대상 | 결과 |
|---|---|
| 웹 브라우저 (claude.ai / Gemini / ChatGPT) | ✅ 완전 캡처 |
| 네이티브 데스크톱 앱 (Claude Desktop, Electron) | ✅ 완전 캡처 — 웹과 바이트 단위로 동일 |

즉 **"앱도 웹만큼 잘 보인다"는 건 이미 실측으로 증명됐다.** 다만 이게 전부 뚫린다는 뜻은
아니고, 직접 확인한 **진짜 벽**이 두 개 남아 있다.

- **인증서 고정(Pinning)하는 앱** — 사내 rootCA를 아무리 신뢰 저장소에 심어도, 그 앱이
  자기가 아는 인증서만 믿게 하드코딩돼 있으면 원천적으로 못 뚫는다. (지금까지 테스트한
  Claude Desktop은 안 걸렸지만, ChatGPT/Gemini 네이티브 앱은 아직 안 봄 — 걸릴 수도 있음)
- **QUIC 강제 사용 앱** — TCP로 안 내려오면 우리 프록시는 애초에 그 패킷 자체를 못 봄

이 둘은 배포 방식(WFP든 뭐든)과 무관하게 **아예 다른 종류의 벽**이라, "제품화하면 다
뚫린다"고 말하면 안 된다.

### 4.2 "감청"이라는 단어 — 더 중요한 지점

"감청"은 한국에서 통신비밀보호법상 **무단으로 남의 통신 내용을 엿듣는다는 뉘앙스**가
강한 단어다. 그런데 이 기술 자체(TLS MITM으로 암호문을 평문으로 보는 것)는 **누가, 어떤
조건으로 하느냐에 따라 완전히 다른 법적 지위**를 갖는다.

- **회사 소유 기기 + 사전 고지(보안 정책 동의)** 위에서, 회사가 자기 자산을 들여다보는
  거라면 — 이건 이미 Zscaler·Netskope·Symantec 같은 기업용 DLP/보안 프록시 회사들이
  전세계적으로 파는 정상적인 제품 카테고리다. "감청"이 아니라 **"고지된 자산 보안
  모니터링"**으로 분류된다.
- **고지 없이, 또는 개인 소유 기기**에서 이걸 하면 — "감청" 쪽 리스크가 실제로 생긴다.

즉 기술은 이미 증명됐고, **관건은 "회사가 이걸 어떤 고지·동의 체계 위에 올리느냐"라는
법무/정책 문제**다. 이건 엔지니어링 영역이 아니라, 사내 법무팀이 "직원 대상 보안
모니터링 정책"으로 정식 문서화해야 하는 부분이다.

## 5. 제품화 관점 결론

제품화 측면에서는, AI 앱(웹·데스크톱 클라이언트 모두)을 **"기본적으로 가시성을 확보하되
한계를 명시한 채로 제공하는 DLP 모듈"**로 접근할 수 있다.

**커버되는 것:** 3사 웹 서비스와, 인증서를 고정하지 않는 Electron 기반 데스크톱 앱(Claude
Desktop이 실증 사례)은 사내 rootCA를 표준 배포 경로(GPO/MDM)로 신뢰 저장소에 심고,
프록시를 루프백이 아닌 위치(별도 호스트) 또는 WFP 커널 리다이렉트로 배치하면 **앱마다
수동 개입 없이 자동으로 잡힌다.** 이 경로에서는 파일 업로드의 파일명·크기·해시·매직바이트
검증까지 포함한 완전한 감사 기록을 남길 수 있다.

**명시해야 하는 한계:** 인증서 고정을 쓰는 네이티브 앱과 QUIC을 강제하는 앱은 이 방식으로
원천적으로 안 잡힌다는 것을 제품 스펙에 **숨기지 않고 명시**해야 한다 — 이걸 "탐지 사각
지대 목록"으로 관리하는 것 자체가 제품 신뢰도의 일부다. 그리고 이 전체가 합법적으로
서려면, 회사 소유 기기에 대한 **사전 고지·동의 기반 보안 모니터링 정책** 위에서 배포되는
것이 전제이며, 이건 코드가 아니라 법무·인사 정책이 먼저 정리돼야 하는 영역이다.
